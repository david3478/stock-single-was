# ADR 0007. 체결은 불변 계획 → T2 확정 서비스 → 커밋 후 호가창 반영

- 상태: 채택 (2026-11-19)
- 관련: IMPLEMENTATION_GUIDE §5.2, ADR 0001, ADR 0005 ③

## 맥락

EA 초기 설계의 대기주문목록에는 `체결상대찾기(들어온주문): Optional<주문>`만 있었다. 인계서는 "DB 커밋 후 메모리 변경을 확정"하라고 한다.
커밋 전에는 목록을 바꿀 수 없으므로 같은 함수를 다시 호출하면 같은 상대가 나온다. 이 방식으로는 매수 100주가 매도 30주 + 70주와 체결되는 경우를 계산할 수 없다.
T2를 어느 클래스가 여는지도 정해져 있지 않았다.

## 결정

1. `OrderBook.plan(입력주문, 처리순번)`은 호가창을 바꾸지 않고 불변 `MatchPlan`을 만든다. 상대들을 가격·seq 순으로 훑으며 임시 잔량을 계산해 여러 체결을 한 계획에 담는다.
2. `MatchConfirmService.confirm(종목, 계획)`이 T2 하나를 담당한다. 종목 워커와 다른 Spring Bean이어야 트랜잭션 프록시가 적용된다.
   - 관련 계좌를 ID 오름차순으로 잠근다(ADR 0009).
   - 입력 주문은 `status = 'RECEIVED'` 조건으로 갱신하며 seq를 처음 부여한다. 0행이면 중복 전달이므로 `false`를 반환한다.
   - 상대 주문은 예상 잔량 조건으로 갱신한다. 0행이면 메모리와 DB가 어긋난 것이므로 예외로 전체 롤백한다.
   - 체결 저장, 양쪽 정산, 양쪽 알림 저장을 같은 T2에 묶는다.
3. 워커는 `confirm`이 정상 반환한 뒤에만 `OrderBook.apply(계획)`을 호출하고 seq를 올린다.
4. `apply`는 계획을 만든 뒤 호가창이 바뀌었으면 아무것도 바꾸지 않고 예외를 던진다.
5. 데드락(`PessimisticLockingFailureException`)이면 워커가 T2 전체를 새 트랜잭션으로 재시도한다. 그 밖의 예외는 해당 종목 워커를 멈춘다.
6. 체결가는 먼저 대기하던 주문의 가격이다.

## 근거

- T2가 실패하면 계획을 버리기만 하면 된다. 메모리를 되돌리는 코드가 없으므로 되돌리기 버그도 없다.
- 계획과 확정을 나누면 매칭은 DB 없이, T2는 실제 MySQL로, 순서 규칙은 mock으로 따로 테스트할 수 있다.

## 결과와 비용

- 주문 하나를 처리할 때마다 계획 객체를 하나 만든다.
- 종목 워커가 멈추면 그 종목 주문은 DB에 RECEIVED로 쌓인다. 자동 종목 복구는 7단계에서 추가한다.
- 커밋 결과를 알 수 없는 경우(ADR 0005 ②)의 처리는 아직 구현하지 않았다.

## 검증

- `OrderBookTest`: 계획이 호가창을 바꾸지 않음, 여러 상대 체결, 오래된 계획 반영 거부.
- `MatchConfirmServiceTest`: 이미 처리된 주문이면 아무것도 바꾸지 않음, 상대 불일치 시 전체 롤백.
- `SymbolWorkerTest`: 커밋 실패 시 호가창·seq 불변, 데드락 재시도, 재시도 한도 초과.

## 재검토 조건

마이크로배치로 여러 주문을 한 T2에 묶을 때.
