# ADR 0003. 알림은 전역 AUTO_INCREMENT + INSERT 전 계좌 잠금

- 상태: 채택 (2026-11-09)
- 관련: IMPLEMENTATION_GUIDE §5.5, QAS 5

## 맥락

SSE 클라이언트는 마지막으로 받은 알림 ID를 기억하고, 재연결하거나 신호를 받으면 `account_id = ? AND id > 마지막ID`로 이어서 조회한다.

AUTO_INCREMENT 번호는 INSERT 시점에 발급되고 다른 트랜잭션에는 커밋 이후에 보인다. 따라서 같은 계좌에서 다음 순서가 생길 수 있다.

| 시간 | 종목 X 워커 (계좌 A) | 종목 Y 워커 (계좌 A) |
|---|---|---|
| ① | 알림 INSERT → 101 발급 | |
| ② | 커밋 전 | 알림 INSERT → 102 발급 |
| ③ | 계속 진행 중 | 커밋, 클라이언트가 102 수신 → 마지막ID=102 |
| ④ | 커밋 | |

④ 이후 클라이언트는 `id > 102`만 조회하므로 101을 영구히 놓친다.

서로 다른 계좌라면 문제가 없다. 조회가 계좌별이므로 계좌 B 클라이언트는 계좌 A의 101을 기다리지 않는다. 문제는 **같은 계좌**의 알림이 서로 다른 트랜잭션에서 엇갈릴 때만 생긴다.

## 결정

1. 알림 ID는 전역 `notifications.id` AUTO_INCREMENT를 쓴다.
2. 알림을 저장하는 트랜잭션은 **INSERT 전에** 알림 대상 계좌 행을 잠그고, 잠금은 커밋까지 유지한다(InnoDB 기본 동작).
3. 정산이 없는 경로에서도 잠근다. 특히 **상대 주문이 없어 대기 등록만 하는 T2**는 계좌를 UPDATE하지 않으므로 `SELECT ... FOR UPDATE`로 명시적으로 잠근다.
4. 한 트랜잭션이 여러 계좌를 잠글 때는 트랜잭션 시작 직후 관련 계좌 전체를 **계좌 ID 오름차순**으로 먼저 잠근 뒤 정산과 INSERT를 한다.
5. 알림 저장은 하나의 API(`NotificationWriter.append(계좌ID들, 이벤트들)`)로만 한다. 이 API가 정렬 → 잠금 → INSERT를 수행한다. 저장소에 직접 INSERT하는 다른 경로를 만들지 않는다.
6. 데드락이 발생하면 T2 전체를 재시도한다. 메모리 호가창은 커밋 후에만 반영하므로 재시도해도 안전하다.

## 근거

- 같은 계좌 알림을 쓰는 트랜잭션들이 잠금으로 직렬화되므로, 같은 계좌 안에서는 ID 발급 순서와 커밋 순서가 같다. 따라서 `id > 마지막ID` 커서가 커밋된 알림을 건너뛰지 않는다.
- 전역 ID는 별도 카운터 컬럼이 필요 없고 프로토타입과 같은 구조라 비교하기 쉽다.
- 저장 API를 하나로 두면 이후 새 알림 경로가 생겨도 잠금을 빠뜨릴 수 없다.

## 고려했으나 선택하지 않은 대안

- **계좌별 연속 번호** (`accounts.next_notification_seq`를 같은 잠금 안에서 증가): 비용은 거의 같고, 번호가 연속이라 클라이언트가 빈 번호를 직접 감지할 수 있다. 현재는 전역 ID의 단순성을 택하고, QAS 5 측정에서 누락 감지가 어렵다면 재검토한다.
- **잠금 없이 전역 ID만 사용**: 위 표의 누락이 발생하므로 제외한다.

## 결과와 비용

- 대기 등록 경로에도 계좌 잠금이 하나 추가된다. 체결이 소수 계좌에 몰리면 이 잠금이 병목 후보가 된다. QAS 2·3 측정에서 계좌 잠금 대기 시간을 기록한다.
- 전역 ID에는 롤백으로 인한 빈 번호가 생길 수 있다. 커서가 `>` 비교이므로 정확성에는 영향이 없지만, 빈 번호를 누락의 증거로 쓸 수는 없다.

## 검증

1. **결정적 재현 테스트**: 트랜잭션 A(종목 X, 계좌 1, 대기 등록)를 알림 INSERT 직후 커밋 직전에 latch로 멈춘다. 트랜잭션 B(종목 Y, 계좌 1, 체결)는 A가 커밋할 때까지 알림 ID를 발급받지 못해야 한다. 잠금이 없는 테스트 전용 경로에서는 같은 시나리오에서 커서가 A를 놓치는 것을 확인해, 테스트가 실제로 결함을 잡아낸다는 것을 보인다.
2. **스트레스 테스트**: 같은 계좌에 여러 종목 워커가 동시에 알림을 만들고, 별도 스레드가 `id > lastId`로 계속 조회한다. 수집한 ID 집합과 DB의 최종 집합이 같아야 한다.
3. **SSE 끝단 테스트**: 한 연결에서 재전송과 새 신호가 겹쳐도 송신이 직렬화되고, 클라이언트가 받은 집합이 DB와 같다. 누락과 중복을 따로 집계한다.

모두 Testcontainers MySQL 8.4(`innodb_autoinc_lock_mode=2`)에서 실행한다.

## 재검토 조건

- 체결 서버를 분리해 알림을 쓰는 프로세스와 SSE를 보내는 프로세스가 달라질 때.
- 계좌 잠금 대기가 측정에서 병목으로 확인될 때.
