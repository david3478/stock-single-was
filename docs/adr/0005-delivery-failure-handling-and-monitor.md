# ADR 0005. 대기열 전달 실패는 즉시 처리하고, 주기 감시는 상태 불일치만 본다

- 상태: 채택 (2026-11-09). ③ 종목 단위 복구와 감시의 자동 복구 실행은 ADR 0013으로 보류
- 관련: IMPLEMENTATION_GUIDE §5.1, §5.2, §5.4, ADR 0002, ADR 0004

## 맥락

T1이 커밋된 주문은 종목 대기열에 전달되어야 한다. 인계서는 "살아 있는 프로세스에서 전달만 실패해도 주문이 영구 대기하지 않도록 재전달 경로를 둔다"고 요구한다.

처음 검토한 방식은 "일정 시간 이상 `RECEIVED`인 주문을 주기적으로 다시 넣는" 스위퍼였다. 이 방식은 두 가지 문제가 있다.

- QAS 3처럼 정상적으로 적체된 주문도 오래 `RECEIVED`로 남는다. 스위퍼가 이미 대기열에 있는 주문을 다시 넣어 부하가 가장 클 때 부하를 더한다.
- 단일 WAS에서 대기열은 같은 프로세스의 메모리 큐다. 전달 실패는 그 자리에서 반환값이나 예외로 알 수 있으므로 시간으로 추정할 이유가 없다.

주기적 재전달(Outbox 릴레이)이 필수인 경우는 보내는 쪽이 실패 여부를 알 수 없을 때, 즉 프로세스 경계나 네트워크를 넘을 때다.

## 결정

**주기적 재전달은 두지 않는다(단일 WAS 한정).** 전달 실패는 원인별로 그 자리에서 처리한다.

| 경우 | 발생 조건 | 처리 |
|---|---|---|
| ① 대기열 넘침 | 상한 큐의 `offer()`가 false | 해당 종목에 넘침 표시를 한다. 워커는 큐를 비운 뒤 DB에서 그 종목의 `RECEIVED` 주문을 ID 순으로 읽어 처리하고, 남은 것이 없으면 표시를 해제한다. |
| ② 커밋 결과 불명 | 커밋은 됐는데 커넥션 오류 등으로 예외 발생 | 주문 ID 또는 `(account_id, client_order_id)`로 DB를 조회한다. 주문이 있으면 대기열에 전달하고 접수 성공으로 응답한다. |
| ③ 종목 엔진 이상 | 커밋 후 메모리 반영 실패, 워커 예외 정지, 전달 중 예상하지 못한 예외 | 해당 종목만 주문 처리를 멈추고 **종목 단위 복구**를 실행한다. 호가창과 대기열을 DB에서 다시 구성한다. |

- 재시작 복구, ③의 종목 단위 복구, QAS 6의 종목 추가 준비는 같은 복구 코드를 사용한다.
- 종목 단위 복구는 워커를 멈춘 상태에서 대기열을 통째로 다시 만들므로 중복 전달이 생기지 않는다.
- 같은 주문이 어떤 이유로든 두 번 전달되면 워커는 `status <> 'RECEIVED'`인 주문을 건너뛰고, T2의 `UPDATE ... WHERE status = 'RECEIVED'`가 0행이면 롤백한다.

**주기 감시**를 둔다. 감시는 시간 추정이 아니라 상태 불일치를 본다.

- 메트릭(종목별): DB의 `RECEIVED` 건수, 가장 오래된 `RECEIVED` 주문의 대기 시간, 대기열 길이, 넘침 표시 여부.
- 이상 판정: **대기열이 비어 있고 넘침 표시가 없으며 워커가 처리 중인 주문이 없는데, DB에 그 종목의 `RECEIVED` 주문이 있다.**
- 이 조건이 연속 두 번 관찰되면 경고 로그를 남기고 ③ 종목 단위 복구를 실행한다. 한 번만 보고 판단하지 않는 이유는 T1 커밋 직후, 대기열 전달 직전의 정상적인 순간을 오판하지 않기 위해서다.
- 감시 조회는 영구 커서를 쓰지 않는다. 매번 종목별 `RECEIVED` 존재 여부와 최솟값을 조회한다(ADR 0002의 커서 주의사항).

## 근거

- 예상한 실패는 모두 발생 지점에서 감지할 수 있으므로, 즉시 처리가 시간 기준 재전달보다 단순하고 정상 적체와 헷갈리지 않는다.
- 감시는 예상하지 못한 버그(전달을 빠뜨린 코드 경로 등)로 주문과 예약금이 재시작 전까지 묶이는 일을 막는다.
- 정상 적체 중에는 대기열이 비어 있지 않으므로 이상 판정 조건과 겹치지 않는다.
- 감시 메트릭은 QAS 3에서 대기열 체류를 보여주는 데 그대로 쓰인다.

## 결과와 비용

- 감시 조회가 주기적으로 실행된다. `(symbol_code, status, id)` 인덱스로 종목별 존재 여부와 최솟값만 읽어 비용을 제한한다.
- 감시가 복구를 실행하는 동안 해당 종목의 처리가 잠시 멈춘다.

## 검증

- ① 상한을 작게 설정한 테스트에서 넘친 주문이 모두 처리되고 중복 체결이 없다.
- ② 커밋 후 예외를 주입한 테스트에서 주문이 처리되고 응답이 접수 성공이다.
- ③ 커밋 후 메모리 반영 실패를 주입하면 해당 종목만 복구되고 다른 종목은 계속 처리된다.
- 감시: 대기열 전달을 의도적으로 건너뛴 주문을 만들면 감시가 감지해 처리한다. 정상 적체(대기열이 찬 상태)에서는 감지하지 않는다.

## 재검토 조건

체결 서버를 분리해 주문 서버와 체결 서버 사이 전달이 네트워크를 넘을 때. 이때는 주기적 재전달(Outbox 릴레이)과 수신 측 중복 제거를 다시 설계한다.
