# ADR 0009. 잠금 순서는 계좌 행 → 보유 행, 알림은 체결 1건당 계좌별 1행

- 상태: 채택 (2026-11-19)
- 관련: ADR 0003, IMPLEMENTATION_GUIDE §5.3, §5.5
- ADR 0003 ⑤를 보완한다(아래 3).

## 맥락

1. 매도 접수(T1)는 보유 행을 갱신한 뒤 주문을 INSERT한다. `orders.account_id` 외래키 검사는 계좌 행에 공유 잠금을 요청한다.
   체결 정산(T2)은 계좌 행을 먼저 잠그고 보유 행을 갱신한다. 같은 계좌에서 둘이 동시에 일어나면 서로를 기다리는 데드락이 생긴다.
2. 알림을 "주문 결과 하나"로 묶을지 "체결 1건"마다 만들지 정해지지 않았다.
3. ADR 0003 ⑤는 "알림 저장 API가 정렬 → 잠금 → INSERT를 한다"고 했다. 그런데 T2는 정산 때 이미 계좌를 잠근다. 알림 저장 시점에 처음 잠그면 잠금 순서가 정산과 엇갈릴 수 있다.

## 결정

1. 모든 트랜잭션은 계좌 행 → 보유 행 순서로 잠근다.
   - T1(매수·매도 모두)은 예약 전에 `SELECT ... FOR UPDATE`로 계좌 행을 먼저 잠근다.
   - T2는 시작하자마자 관련 계좌 전부를 ID 오름차순으로 잠근다(ADR 0003 ④).
2. 알림은 체결 1건마다 양쪽 계좌에 1행씩(`trade_id` 있음), 상대 없이 대기 등록되면 입력 주문 계좌에 1행(`trade_id` 없음)이다. `ck_notifications_trade` CHECK로 강제한다.
3. 계좌 잠금은 `MatchConfirmService`가 T2 시작 때 한 번 한다. `NotificationWriter`는 잠그지 않고 INSERT만 하며, 알림 INSERT는 이 클래스로만 한다.
   ADR 0003의 목적(같은 계좌의 알림 ID 발급 순서 = 커밋 순서)은 그대로 지켜진다. 알림 INSERT가 항상 계좌 잠금을 쥔 T2 안에서 일어나기 때문이다.

## 근거

- 잠금 순서를 하나로 고정하면 같은 계좌의 접수와 정산 사이에 교차 대기가 생기지 않는다.
- 체결 단위 알림이면 QAS 5에서 "받아야 할 알림 집합"을 payload를 풀지 않고 `trades`와 `notifications`의 SQL로 셀 수 있다.
- 늦은 잠금을 대체 경로로 두면 잠금 누락 버그가 조용히 데드락으로 바뀐다. 잠금 책임을 한 곳에 둔다.

## 결과와 비용

- 매수 T1도 계좌 행을 한 번 더 조회한다. 같은 계좌의 접수는 직렬화된다.
- 주문 하나가 여러 상대와 체결되면 그 계좌에 알림이 여러 건 간다.

## 검증

- `OrderIntakeServiceTest`: 같은 계좌의 동시 매도 8건 중 1건만 성공.
- `MatchConfirmServiceTest`: 체결마다 양쪽 알림, 대기 등록은 `trade_id` 없는 알림.
- ADR 0003의 검증 테스트 3종(결정적 재현, 스트레스, SSE 끝단)은 6단계에서 작성한다.

## 재검토 조건

계좌 잠금 대기가 측정에서 병목으로 확인될 때. 체결 서버를 분리할 때.
