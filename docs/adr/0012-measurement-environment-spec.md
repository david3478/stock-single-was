# ADR 0012. 측정 환경 사양: 앱 m7i.large, RDS db.m7g.large, 같은 AZ, 측정할 때만 켜는 부하 생성기

- 상태: 채택 (2026-11-27)
- 관련: ADR 0011, IMPLEMENTATION_GUIDE §13, §294, §314, §319, §323
- ADR 0010의 사양(`t3.small` 한 대, JVM 힙 512MB, InnoDB 버퍼 256MB)을 대체한다.

## 맥락

ADR 0011로 앱(Nginx + Spring)과 DB(RDS)를 분리했지만 사양은 정하지 않았다.
이 배포 환경은 데모뿐 아니라 10단계 QAS 측정에도 쓴다. 가이드는 별도 부하 생성기, 앱·DB·생성기 사양 기록,
같은 사양에서의 비교를 요구한다(§13, §319).

## 결정

### 사양과 배치

| 역할 | 사양 | 켜는 때 |
|---|---|---|
| 앱 EC2 (Nginx + 앱 컨테이너) | `m7i.large` (2 vCPU, 8 GiB, x86) | 데모·측정할 때 |
| RDS MySQL 8.4 | `db.m7g.large` (2 vCPU, 8 GiB), Single-AZ, gp3 20GB | 데모·측정할 때 |
| 부하 생성기 EC2 | `c7i.xlarge` (4 vCPU, 8 GiB). 보정에서 모자라면 `c7i.2xlarge` | 측정할 때만 |

1. 앱 EC2, RDS, 부하 생성기는 모두 같은 AZ(`ap-northeast-2a`)에 둔다.
2. 부하 생성기는 앱 EC2의 사설 IP로 요청한다. 앱 EC2 보안 그룹은 내 IP와 부하 생성기 보안 그룹에서 오는 80만 받는다.
3. 앱 JVM 최대 힙은 4GB(`-Xmx4g`)다.

### 측정 전 보정

본 측정 전에 부하 생성기가 낼 수 있는 최대 유입을 먼저 잰다.

- 대상: 앱 EC2의 Nginx에 둔 고정 응답 주소. 주문 POST에는 즉시 `202`와 고정 본문을 주고, SSE 주소에는 연결유지 신호만 보낸다.
  앱과 DB를 거치지 않으므로 생성기 자신의 한계만 드러난다.
- 요청 모양은 본 측정과 같게 한다(같은 JSON 본문, 같은 응답 검사, 같은 SSE 연결 수). 정적 파일 GET은 생성기 부담이 훨씬 작아 한계를 과대평가한다.
- 통과 기준: 본 측정 최대 목표 유입의 2배 이상(최소 초당 1만 건)을 1분 동안 `dropped_iterations` 0, 생성기 CPU 1초 샘플 모두 80% 미만으로 낸다.
- 통과하지 못하면 생성기를 `c7i.2xlarge`로 올려 다시 보정한다.

### 측정 판정

생성기 CPU는 1초 간격으로 기록한다. 평균으로는 10초짜리 폭주 구간의 포화가 가려진다.

| 상황 | 판정 |
|---|---|
| 생성기 CPU가 80% 이상인 1초 구간이 있다 | 무효. 생성기를 키워 다시 측정한다 |
| `dropped_iterations` > 0, 생성기 CPU 여유, VU가 최대치까지 응답을 기다리고 있다 | 시스템 불합격. 응답이 늦어 유입을 받지 못한 것이므로 QAS 실패로 센다 |
| `dropped_iterations` > 0, 생성기 CPU 여유, VU도 남아 있다 | 무효. 생성기 설정(VU 수 등) 문제다 |

### 측정 전 필수 조건

- Nginx `worker_connections`를 올린다. 프론트 이미지 기본값은 1024이고 `worker_processes auto`라 `m7i.large`에서 연결 약 2,048개다.
  SSE 연결 하나가 Nginx에서 연결 2개(브라우저 쪽, 앱 쪽)를 쓰므로 동시 SSE 약 1,000개에서 막힌다. 값은 10단계에서 SSE 연결 수를 정할 때 함께 정한다.

### 매 측정 기록

앱·RDS·생성기 인스턴스 유형과 AZ, AMI, 앱·프론트 이미지 digest, JVM 옵션, RDS 파라미터(버퍼 풀, 격리 수준, 내구성 설정),
생성기 CPU 1초 샘플, `dropped_iterations`, 최대 VU 사용량.

## 근거

1. **버스트형(t 계열)을 쓰지 않는다.** CPU 크레딧 잔량에 따라 처리량이 바뀌어 같은 측정을 반복해도 결과가 달라진다. m7i·m7g는 성능이 고정이다.
2. **같은 AZ.** T2 한 번에 앱과 DB가 여러 번 주고받으므로 AZ 간 지연과 그 흔들림이 체결 지연에 그대로 더해진다. AZ 간 전송 요금도 피한다.
3. **앱과 DB 모두 8 GiB.** 앱은 종목 워커, 송신 스레드, HTTP 스레드, 메모리 호가창을 함께 돌린다. DB는 시험 계좌 10만 개 데이터를 InnoDB 버퍼에 담아야 한다(RDS 기본 버퍼 풀은 메모리의 약 3/4).
4. **부하 생성기는 따로, 측정할 때만.** 같은 서버에서 부하를 만들면 CPU를 나눠 써 측정이 오염된다(가이드 §319). 측정할 때만 켜므로 4~8 vCPU로 올려도 비용 부담이 작다.
5. **보정과 판정을 나눈다.** 생성기 한계를 먼저 알면 본 측정의 실패가 앱 문제인지 생성기 문제인지 구분할 수 있다.
   `dropped_iterations`는 생성기가 약할 때와 앱이 느릴 때 모두 생기므로, 원인을 나누지 않고 모두 무효로 하면 과부하 측정이 끝나지 않는다.

## 결과와 비용

서울 리전 온디맨드(AWS Pricing API, 2026-11-27 조회, 세금 별도).

| 자원 | 시간당 |
|---|---|
| `m7i.large` | $0.1239 |
| `db.m7g.large` MySQL Single-AZ | $0.2344 |
| `c7i.xlarge` / `c7i.2xlarge` | $0.2016 / $0.4032 |
| 퍼블릭 IPv4(켜진 인스턴스마다) | $0.005 |
| EBS gp3 / RDS gp3 스토리지(꺼도 과금) | $0.0912 / $0.131 per GB-월 |

- 앱 + RDS를 하루 4시간 × 30일 켜면 월 약 $48(스토리지 포함). 생성기 `c7i.xlarge`는 측정 1시간당 약 $0.21.
- RDS는 중지해도 7일 뒤 자동으로 다시 켜진다. 잊고 켜 두면 RDS만 하루 $5.6, 한 달 $171이다. 측정 기간이 끝나면 스냅샷을 남기고 삭제한다.
- 측정 전 Nginx 설정 변경과 보정 실행이 한 단계 늘어난다.

## 검증

- 배포 후 앱 EC2와 RDS의 AZ가 같은지 `describe-instances`, `describe-db-instances`로 확인한다.
- 앱 컨테이너의 JVM 최대 힙이 4GB인지 확인한다.
- 10단계에서 보정 결과(최대 유입, CPU 샘플)를 측정 기록에 남긴다.

## 재검토 조건

- 보정에서 `c7i.2xlarge`로도 통과하지 못할 때(생성기 여러 대로 나눈다).
- 측정에서 DB나 앱 사양이 병목으로 확인되어 사양을 바꿔 비교할 때. 이때는 같은 자원 예산 비교와 자원을 늘린 비교를 구분해 기록한다(가이드 §323).
