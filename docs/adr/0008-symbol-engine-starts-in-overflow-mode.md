# ADR 0008. 종목 엔진은 DB에서 복원하고 넘침 상태로 시작한다

- 상태: 채택 (2026-11-19)
- 관련: IMPLEMENTATION_GUIDE §5.4, §5.6, ADR 0002, ADR 0005

## 맥락

기동, 종목 추가(QAS 6), 종목 단위 복구(ADR 0005 ③)는 모두 "종목 엔진을 새로 만들고 DB와 맞추는" 일이다.
경로가 셋으로 갈라지면 한쪽만 고쳐지는 버그가 생긴다.
엔진을 교체하는 동안 커밋된 주문이 옛 엔진으로 전달되는 경쟁도 있다. 이를 막으려고 모든 접수(T1)에 수명주기 잠금을 거는 안을 검토했다.

## 결정

1. `SymbolPreparer.prepare(종목)` 하나가 기동·추가·복구의 공통 경로다.
   1. 같은 종목의 기존 워커를 멈추고 대기열 등록을 해제한다.
   2. DB의 OPEN·PARTIALLY_FILLED 주문을 가격과 원래 seq로 호가창에 복원한다.
   3. 다음 seq = 종목 전체 주문의 `MAX(seq) + 1`. FILLED까지 포함해야 기존 순번과 겹치지 않는다.
   4. 대기열을 **넘침 상태로** 만들어 전달기에 등록하고 워커를 시작한다.
2. 넘침 상태의 워커는 DB의 RECEIVED를 ID 순으로 읽어 처리한다(ADR 0005 ①과 같은 경로). 비면 넘침을 해제하고 한 번 더 조회한다.
3. 접수(T1)에는 수명주기 잠금을 걸지 않는다.

## 근거

- 넘침 상태로 시작하면 재기동 시 RECEIVED 10만 건을 큐에 넣을 필요가 없다. 큐 용량과 무관하게 DB가 원본이다.
- 엔진 교체 중 옛 엔진으로 간 주문도 DB에는 RECEIVED로 남아 있으므로 새 엔진의 DB 조회에 걸린다. 큐와 DB 양쪽에서 같은 주문이 와도 워커가 RECEIVED가 아니면 건너뛴다.
- 수명주기 잠금은 매 접수마다 DB 트랜잭션 동안 잠금을 쥐게 한다. 드문 복구 경로를 위해 주문 처리 경로 전체에 비용을 매기는 셈이라 채택하지 않았다.

## 결과와 비용

- 엔진을 시작한 직후에는 큐 대신 DB 조회로 주문을 처리한다. 적체가 없으면 첫 조회에서 넘침이 해제된다.
- 대기 주문 복원은 아직 한 번에 전부 읽는다. 10만 건 묶음 조회, readiness, 자동 종목 복구, 주기 감시는 7단계다.

## 검증

- `OrderFlowIntegrationTest`: 엔진 시작 전에 접수된 주문이 엔진을 띄우면 처리됨, DB의 대기 주문이 복원되고 seq가 이어짐.
- `SymbolWorkerTest`: 넘침 중 DB 처리 후 해제, 해제 중 새 주문이 보이면 넘침 유지.
- `OrderDispatcherTest`: 넘침 중에는 자리가 나도 새 주문을 큐에 넣지 않음.

## 재검토 조건

체결 서버를 분리해 접수 서버와 엔진이 다른 프로세스가 될 때.
