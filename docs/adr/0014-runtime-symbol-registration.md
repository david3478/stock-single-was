# ADR 0014. 실행 중 종목 추가: 준비중 등록 → 엔진 준비 → 활성화, 같은 요청 재시도로 완료

- 상태: 채택 (2026-11-27)
- 관련: QAS 6(IMPLEMENTATION_GUIDE §5.6, §10), ADR 0004, ADR 0008, ADR 0011, EA `symbol-add`

## 맥락

QAS 6은 운영 중에 코드 수정·재배포 없이 신규 종목을 추가하고, 기존 종목 처리를 중단하지 않으며, 신규 종목이 주문을 받을 준비(ACTIVE)가 되는 것을 요구한다.
가이드 §5.6은 "DB 등록(준비 중) → 대기열·워커·목록 준비 → 활성화 → 주문 허용" 순서와 중간 실패·재시도 처리를 요구한다.

이미 있는 것: `symbols.status`(PREPARING/ACTIVE), ACTIVE가 아닌 종목의 주문 거절, 종목 엔진을 만드는 공통 경로 `SymbolPreparer.prepare()`(ADR 0008).
없는 것: 등록 요청을 받아 위 순서를 지키는 API와 서비스. 단일 WAS와 종목별 워커 구조를 전제로 한다(다중 체결 서버는 다루지 않는다).

## 결정

1. **등록 API**: `POST /api/symbols` `{"code", "name"}`(EA 종목관리Controller.종목추가 → 종목등록Service.종목추가).
2. **순서**: ① 종목DAO.준비중등록(`PREPARING`으로 INSERT) → ② `SymbolPreparer.prepare(code)`로 빈 호가창·대기열·워커 준비 →
   ③ 종목DAO.활성화(`UPDATE ... SET status = 'ACTIVE' WHERE code = ? AND status = 'PREPARING'`).
   엔진을 준비한 뒤에 활성화한다. 접수는 ACTIVE 종목만 받으므로 주문은 엔진이 준비된 뒤에만 들어온다.
3. **응답은 활성화가 끝난 뒤에 한다**(동기). 새로 활성화하면 `201`, 이미 ACTIVE면 `200`, 같은 코드가 다른 이름으로 있으면 `409`, 형식 오류는 `400`.
   QAS 6 시험은 이 응답과 종목 목록 조회로 ACTIVE를 확인한다.
4. **같은 요청 재시도로 완료한다**. 어느 단계에서 실패해도 같은 요청을 다시 보내면 남은 단계를 이어서 끝낸다.

   | 실패 지점 | DB 상태 | 재시도 시 |
   |---|---|---|
   | ① 전 | 없음 | 처음부터 |
   | ① 후 ② 전 | PREPARING, 엔진 없음 | ②③ |
   | ② 후 ③ 전 | PREPARING, 엔진 있음 | 엔진은 그대로 두고 ③ |
   | ③ 후 응답 전 | ACTIVE | 200. 엔진이 없으면 만든다 |

5. **동시 요청**: 같은 코드의 INSERT는 기본 키 중복으로 하나만 성공하고 나머지는 "이미 있음"으로 이어 간다.
   엔진은 `SymbolPreparer.prepareIfAbsent()`가 확인과 생성을 한 잠금 안에서 해서 하나만 만들고, 이미 있으면 다시 만들지 않는다
   (이미 주문을 받고 있을 수 있는 엔진을 재생성하지 않기 위해서다). 활성화는 조건부 UPDATE라 여러 번 실행돼도 결과가 같다.
6. **서버 재시작 시 PREPARING 종목**: 기동 복구는 ACTIVE 종목만 준비한다. PREPARING으로 남은 종목은 자동으로 활성화하지 않고 기동 로그에 경고로 남긴다. 운영자가 같은 요청을 다시 보내 완료한다.
7. **신규 종목의 보유 주식은 이 기능의 범위가 아니다**. 초기 주식 배정 기능은 만들지 않는다. QAS 6의 첫 체결 검증용 매도 물량은 시험 데이터로 넣는다(가이드 §10).
8. **접근 제한은 두지 않는다**. 로그인이 없는 데모 범위와 같고, 외부 접근은 보안 그룹(내 IP, 부하 생성기)으로만 제한된다(ADR 0011).
9. **DB 커넥션 풀은 운영할 최대 종목 수 기준으로 기동 전에 정한다**. 풀 크기는 기동할 때 읽는 설정이라 실행 중에 바꾸려면 재시작이 필요하고,
   이는 "재배포 없이" 조건과 맞지 않는다. ADR 0004의 기준(종목 워커 수 + HTTP 여유분 이상)을 종목 20개로 계산한 값은 QAS 6 측정 설정에서 확정한다.

## 근거

- 순서를 지키면 "주문은 받았는데 처리할 워커가 없는" 순간이 생기지 않는다. 생기더라도 DB에 RECEIVED로 남아 처리되지만(ADR 0008), 순서로 그 경우 자체를 없앤다.
- 신규 종목은 대기 주문이 없어 엔진 준비가 기존 종목에 영향을 주지 않는다. `prepare()`의 잠금은 엔진을 만들고 바꾸는 동작끼리만 줄 세우고, 실행 중인 기존 워커는 막지 않는다.
  실제로 기존 종목에 영향이 없는지는 QAS 6 측정으로 확인한다.
- 재시도로 완료하는 방식은 주문 접수의 `clientOrderId` 재요청 규칙과 같아서, 별도 상태 기계나 정리 작업이 필요 없다.
- 재시작 때 PREPARING 종목을 자동으로 활성화하면 운영자가 포기한 등록이 의도와 다르게 열릴 수 있다.

## 결과와 비용

- 종목 삭제·거래 정지는 다루지 않는다.
- 데모 화면에는 종목 추가 기능이 없다. 화면은 종목 목록을 처음 열 때만 읽으므로 새 종목은 새로고침해야 보인다.
- 커넥션 풀을 최대 종목 수 기준으로 잡으므로 종목이 적을 때는 커넥션이 남는다.
- 등록 API가 공개되어 있어, 보안 그룹 밖으로 서비스를 열려면 인증이 먼저 필요하다.

## 검증

- 서비스 단위 테스트: 순서(활성화가 엔진 준비보다 먼저 일어나지 않음), 단계별 실패 후 재시도로 완료, 이미 ACTIVE면 200, 이름 충돌 409.
- HTTP → DB 통합 테스트: 추가 전 주문 거절 → 추가(201) → 매수·매도 체결, 같은 요청 재시도(200), 동시 요청에도 엔진 하나, 기존 종목 처리 중 추가해도 기존 종목 거절·미처리 0.
- QAS 6 측정(10단계): 가이드 §10의 네 가지.

## 재검토 조건

- 체결 서버를 여러 대로 나눌 때(종목 배정, 버전 동기화).
- 운영 중 커넥션 풀이나 종목 수 상한이 병목으로 확인될 때.
