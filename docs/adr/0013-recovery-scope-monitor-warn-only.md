# ADR 0013. 7단계는 기동 복구와 감시 경고까지, 종목 단위 자동 복구는 향후 과제

- 상태: 채택 (2026-11-27)
- 관련: ADR 0005(③과 감시의 자동 복구 실행을 보류), ADR 0002, ADR 0008, IMPLEMENTATION_GUIDE §5.4, QAS 4

## 맥락

ADR 0005는 실행 중 장애를 세 가지로 나눴다. ① 대기열 넘침은 4단계에서 구현했다. ② 커밋 결과 불명, ③ 종목 엔진 이상은
"종목 단위 복구"로 그 종목만 DB에서 다시 만들고, 주기 감시가 상태 불일치를 두 번 연속 보면 ③을 실행한다고 정했다.

QAS 4가 요구하는 것은 **서버를 강제 종료한 뒤 재시작**했을 때 접수 확정 주문을 잃지 않고 거래를 재개하는 것이다.
살아 있는 서버 안에서 종목 하나만 자동으로 다시 만드는 일은 QAS 4의 요구가 아니다.

## 결정

이번 단계에서 구현한다.

1. **기동 복구**: 서버가 뜰 때 ACTIVE 종목마다 `SymbolPreparer.prepare()`(ADR 0008)로 엔진을 만든다.
   대기 주문은 주문 ID 기준으로 정해진 건수씩 이어서 읽는다(`trading.recovery.restore-batch-size`).
2. **readiness**: 모든 종목의 기동 복구가 끝나기 전에는 `/actuator/health/readiness`가 DOWN이다.
   복구 중에도 접수(T1)는 받는다. 그 주문은 DB에 RECEIVED로 남고 엔진이 뜬 뒤 처리된다(ADR 0008).
3. **감시는 메트릭과 경고까지만 한다.** 종목별로 RECEIVED 건수, 가장 오래된 RECEIVED의 대기 시간, 대기열 길이,
   넘침 여부, 워커 상태를 메트릭으로 내보낸다. 상태 불일치(ADR 0005의 판정 조건)를 두 번 연속 보면 경고 로그와
   카운터를 남기고, **복구는 실행하지 않는다.**
4. **워커가 FAILED로 멈추면** 그 순간 에러 로그를 남기고(기존), 감시 메트릭에서 그 종목의 상태가 FAILED로 보이게 한다.
   멈춘 종목은 서버를 재시작하면 기동 복구로 되살아난다.
5. 기동 중 종목 하나의 엔진 준비가 실패하면 지금처럼 서버 기동이 실패한다. 컨테이너 재시작 정책이 다시 띄운다.

향후 과제로 남긴다(설계는 ADR 0005와 아래에 있고 구현하지 않는다).

- **종목 단위 자동 복구**(ADR 0005 ③): 워커 FAILED 또는 감시의 불일치 판정 시 그 종목만 `prepare()`로 다시 만든다.
  - 워커 스레드가 직접 부르면 안 된다. `prepare()`가 옛 워커의 종료를 기다리므로 자기 자신을 기다리며 멈춘다. 별도 복구 스레드가 실행한다.
  - 같은 원인으로 계속 실패하면 복구가 끝없이 반복된다. 재시도 간격을 1초부터 두 배씩 최대 1분까지 늘리고, 실패마다 메트릭과 에러 로그를 남긴다.
- **기동 중 종목 일부 실패 시 나머지만 띄우기**: 실패한 종목은 위 자동 복구로 재시도한다.
- **커밋 결과 불명**(ADR 0005 ②): 같은 `clientOrderId` 재요청이 기존 주문을 돌려주고, RECEIVED면 다시 전달하는 경로가 이미 있다.
  별도 처리 코드는 두지 않는다. 전달이 빠진 주문은 감시 경고로 드러나고 재시작으로 처리된다.

## 근거

- QAS 4의 범위(강제 종료 후 재시작)는 기동 복구만으로 충족된다. 재시작은 메모리를 모두 버리고 DB에서 다시 만들므로,
  실행 중 생길 수 있는 메모리와 DB의 어긋남도 재시작으로 해소된다.
- 자동 복구는 스레드 수명주기와 재시도 정책이 얽혀 테스트할 경우가 많다. 이번 단계의 목표에 비해 위험과 비용이 크다.
- 감시 경고와 FAILED 메트릭이 있으면 "종목이 멈췄는데 아무도 모르는" 상태는 피할 수 있다. 사람이 재시작으로 대응한다.

## 결과와 비용

- 실행 중 종목 엔진이 멈추면 재시작 전까지 그 종목의 주문이 처리되지 않고 예약금·예약 수량이 묶인다. 경고와 메트릭으로 알 수 있다.
- 감시가 5초마다 종목별 RECEIVED 존재 여부를 조회한다. `ix_orders_recovery (symbol_code, status, id)`로 범위만 읽는다.

## 검증

- 단위 테스트: 묶음 복원이 끝까지 이어서 읽는다, readiness가 복원 전 DOWN·후 UP, 감시가 두 번 연속에서만 경고하고 정상 적체에서는 경고하지 않는다, FAILED 워커가 메트릭에 보인다.
- 장애 테스트(Testcontainers): T1 커밋 후 전달 전 종료, T2 커밋 전 실패, T2 커밋 후 메모리 반영 전 종료, 재시작 후 순서·순번 유지. 종료는 엔진을 버리고 DB에서 다시 만드는 것으로 재현한다.
- QAS 4 측정: `docs/measurement/qas4-server-recovery.md` 절차로 EC2에서 강제 종료(`docker kill`) 후 유실 건수와 재시작 시간을 잰다.

## 재검토 조건

- 실행 중 종목 엔진 정지가 실제로 관찰되거나, 재시작 없이 거래를 이어 가야 하는 요구가 생길 때 종목 단위 자동 복구를 구현한다.
