# 10단계 측정 설계 (QAS 2·3·5·6, QAS 4 재측정, 단일 WAS 기준선)

상태: **설계 확정, 도구 구현과 측정 전이다.** 이 문서의 숫자는 시험 조건(설계값)이고 결과가 아니다.
"예상"이라고 쓴 값은 계산으로 잡은 값이며 측정에서 실제 값을 기록한다. 결과는 이번 조건과 관찰한 건수로만 해석한다.

## 1. 공통 규칙

### 1.1 측정 경로와 장비

ADR 0012 그대로: 부하 생성기 `c7i.xlarge`(필요하면 `2xlarge`) → 앱 EC2 `m7i.large`의 **사설 IP** → Nginx → 앱 → RDS `db.m7g.large`, 모두 `ap-northeast-2a`.
결과에 경로, 장비 사양, AMI, 이미지 digest, JVM·RDS·Nginx 설정을 기록한다.

### 1.2 주문 식별과 대조

- k6는 주문마다 **`accountId`, `clientOrderId`, 보낸 시각, HTTP 상태, 응답의 주문번호(있으면)**를 기록한다.
- SSE 수집기는 알림마다 **연결한 계좌, 알림 번호(event id), 주문번호, 종류, 체결번호, 받은 시각**을 기록한다.
- 측정 후 DB `orders`의 유일 키 `(account_id, client_order_id)`로 주문번호·상태를 읽어 세 기록을 잇는다. 주문번호를 HTTP 응답에서만 얻지 않는다.
  HTTP 응답을 못 받았지만 커밋된 주문은 HTTP 결과, DB 저장, 체결, 알림 수신을 각각 기록한다.
- 도착 순서에 의존하지 않는다. 202보다 알림이 먼저 와도 기록만 하고, 대조는 측정이 끝난 뒤 한다.

### 1.3 시계와 단위

- 보낸 시각과 받은 시각은 **같은 부하 생성기의 벽시계, epoch 밀리초**다. k6는 `Date.now()`, 수집기는 `System.currentTimeMillis()`.
- 프로세스마다 기준점이 다른 `System.nanoTime()`·k6 내부 타이머는 서로 빼지 않는다.
- 측정 전후로 생성기의 `chronyc tracking`을 기록한다.
- QAS 5 판정은 시계를 쓰지 않는다(5.2). DB 시각(`created_at`)은 참고 수치에만 쓴다.

### 1.4 "체결 결과"의 정의 (QAS 2·3)

측정 대상 주문의 결과는 **그 주문을 낸 계좌의 SSE로 받은, 주문번호가 일치하고 체결번호가 있는 알림**(`ORDER_FILLED`)이다.
1주 주문이므로 정상이면 체결은 1건이다. OPEN(대기 등록) 알림과 HTTP 202는 체결 결과가 아니다.

### 1.5 주문별 분류 (QAS 2·3)

| 분류 | HTTP | DB | 체결 알림 | 처리 |
|---|---|---|---|---|
| A 정상 | 202 | FILLED, 체결 1건 | 수신 | 지연 = 받은 시각 − 보낸 시각 |
| B 알림 미수신 | 202 | FILLED | 관찰 종료까지 없음 | 실패 |
| C 즉시 체결 안 됨 | 202 | OPEN 등 미체결 | 해당 없음 | 원인 판정(1.6) |
| D HTTP 실패·커밋됨 | 오류·시간 초과 | 있음 | 있거나 없음 | 실패. HTTP, DB, 알림을 따로 기록 |
| E HTTP 실패·커밋 안 됨 | 오류·시간 초과 | 없음 | 없음 | 실패 |
| F 미전송 | 보내지 못함 | 없음 | 없음 | 원인 판정(1.7) |
| G 다중 체결 | — | 체결 2건 이상 | — | 버그. 그 회차 지연 결과를 쓰지 않고 조사 |

세 가지 수를 섞지 않는다.

| 수 | 기준 | 정상이면 |
|---|---|---|
| 주문별 DB 체결 건수 | `trades` | 1 |
| 계좌별 고유 알림 번호 수 | 수집기가 받은 서로 다른 event id | DB의 그 계좌 알림 수와 같다 |
| 알림 번호별 수신 횟수 | 같은 event id를 받은 횟수(연결을 합쳐서) | 1. 2 이상이면 중복 수신 |

### 1.6 즉시 체결 안 됨(C)의 원인 판정

종목 안의 처리는 처리순번(`seq`) 순서이므로, 그 주문을 처리하던 순간 살 수 있던 매도가 남아 있었는지 DB로 재구성한다.
남은 매도 = (그 주문보다 앞선 순번의 사전 매도 수) − (그 주문보다 앞선 순번의 매수가 가져간 체결 수).

| 경우 | 판정 근거 | 회차 처리 |
|---|---|---|
| 시험 준비 오류 | 남은 매도 0(물량 부족), 또는 SQL로 가격·계좌 구성 위반 확인(매도가 1,000원 아님, 매수·매도 계좌 겹침) | 무효. 준비를 고쳐 다시 측정 |
| 시스템 동작 문제 | 남은 매도가 있는데 OPEN | 유효. 그 주문은 실패. 버그로 조사 |
| 원인 불명 | 계산이 맞지 않음 | 판정 보류. 조사 후 재측정 |

### 1.7 미전송(F)과 유입 미달의 원인 판정

계획 수, 실제 전송 수, 미전송 수를 따로 기록한다. 목표 유입에 못 미쳐도 자동으로 무효로 하지 않는다.

| 근거 | 생성기 원인 | 앱 응답 지연 원인 |
|---|---|---|
| 생성기 CPU 1초 샘플 | 높다(80% 이상 구간) | 여유 |
| k6 사용 VU / 최대 VU | 최대에 닿지 않았는데 미전송 | 최대에 닿음 |
| k6 응답 시간 추이 | 변화 없음 | 미전송 시점에 증가 |
| 앱 요청 처리 시간(앱 EC2에서 `/actuator/prometheus` 1초 기록) | 변화 없음 | 증가 |

- 생성기 원인 → 회차 무효(ADR 0012). 앱 응답 지연 원인 → 그 주문은 실패로 분모에 포함. 판단 불가 → 판정 보류.

### 1.8 회차 유효성

- 생성기 CPU 1초 샘플 80% 이상 → 무효(ADR 0012).
- 수집기 상태(6.2)가 밀림 → 무효.
- 측정 전 SSE 연결 완료 신호가 없으면 시작하지 않는다(Last-Event-ID 없는 연결은 연결 이후 알림만 받는 구현이다).
- 원인 불명이 하나라도 있으면 그 회차는 판정 보류, 조사 후 재측정한다.

### 1.9 결과 해석의 한계

- QAS 2·3·5 결과는 **사전 반대 주문을 한 가격에 깔아 두고 1주 주문을 보낸 조건**의 결과다. 부분 체결, 여러 상대와의 체결, 넓게 퍼진 호가 등 다른 주문 패턴으로 일반화하지 않는다.
- DB 계좌는 2,000개이고 실제로 쓰는 계좌는 2.1과 같다. 더 많은 사용자에 대한 보장으로 일반화하지 않는다.

### 1.10 기준·조건 변경 원칙

기준이나 시험 조건을 바꿀 때는 가이드 원칙(§10 "목표를 바꿀 때는 변경 이유와 전후 값을 남긴다")대로 이유와 변경 전후를 기록한다.

## 2. 계좌·사전 주문·SSE 구성

### 2.1 계좌 (측정용 seed)

| 항목 | 값 |
|---|---|
| DB 전체 계좌 | 2,000(계좌마다 현금 1억 원, 종목마다 1,000주) |
| 매수 계좌(측정 대상 주문) | 1~500, 주문마다 돌아가며 사용 |
| 매도 계좌(사전 반대 주문) | 501~1,000, 주문마다 돌아가며 사용 |
| 조회 계좌(QAS 2) | 1,001~2,000, 고르게 |
| SSE 연결 | QAS 2·3: 매수 계좌 500개. QAS 5: 매수·매도 계좌 1,000개 |

매수와 매도 계좌를 나눠 자기 체결을 막는다(엔진에 자기 체결 방지 기능은 없다). 실제 사용 분포(계좌별 주문 수)를 결과에 기록한다.
가이드 §290의 "시험 계좌 10만 개"는 QAS 시험 조건(§10)에 없는 설계 당시의 가정이라 이번에는 쓰지 않는다.

### 2.2 사전 반대 주문과 측정 대상 주문

| 항목 | QAS 2 | QAS 3 | QAS 5 |
|---|---|---|---|
| 측정 대상 주문 | 매수 1주, 지정가 1,100원 | 같음 | 같음 |
| 사전 매도 | 1주씩, 1,000원 한 가격 | 같음 | 같음 |
| 필요 매도(예상 소비) | 75초 × 1,000건 = 75,000 | SYM01 20,000, 나머지 종목당 1,111 | 회차 약 11번 × 주기 약 20초 × 1,000건 = 약 220,000(재연결이 늦으면 주기가 길어져 더 든다) |
| 준비 물량 | 종목당 9,000(여유 20%) | SYM01 25,000, 나머지 종목당 1,500 | 종목당 33,000(330,000, 여유 50%) |

- 매수 지정가(1,100)보다 비싼 매도가 없으므로, 남은 매도가 있으면 반드시 체결된다. 차액 100원은 환불된다.
- 사전 매도는 접수·처리를 끝낸 뒤(RECEIVED 0) 측정을 시작한다. 사전 매도의 OPEN 알림은 측정 대상이 아니다.
- 기록: 사전 매도의 종목·가격·주문당 수량·총 물량, 매수·매도 계좌 수와 분산, 측정 대상 주문의 전량 체결 여부, 측정 끝의 남은 사전 매도 수.
- 보유 확인: QAS 5 매도 계좌는 계좌·종목당 66주를 쓰고 보유는 1,000주라 충분하다.

## 3. QAS 2 주문 처리 시간

| 항목 | 내용 |
|---|---|
| 부하 | 측정 대상 매수 1,000건/초(10종목 각 100건/초) + **계좌 조회** 9,000건/초. 예열 15초 + 측정 60초 |
| 계좌 조회 구성 | 잔고 4,000 / 보유 3,000 / 주문 내역(20건) 2,000 건/초. 호가창(종목 조회)은 넣지 않는다(원래 정의가 "계좌 조회 9,000/s"다, 가이드 변경 기록) |
| 시작 | k6가 측정 대상 주문을 보내기 직전의 `Date.now()` |
| 종료 | 수집기가 그 주문의 체결 알림을 받은 시각(1.4) |
| 판정 대상 | 보낸 시각이 측정 구간(예열 이후 60초)에 있는 계획 주문 전체(미전송 처리는 1.7) |
| **판정** | **판정 대상 중 300ms 안에 체결 알림을 받은 비율 ≥ 99%**. 실패를 지연 무한대로 넣은 P99 ≤ 300ms와 같은 기준이다 |
| 함께 표시 | 성공 주문만의 P50·P95·P99·최대, 분류 A~G 건수(성공·오류·미수신), 계좌 조회 응답 시간, 생성기·앱 CPU, 커넥션 풀 사용·대기, 수집기 상태 |
| 관찰 종료 | 마지막 주문을 보낸 뒤 RECEIVED 0이고 미수신이 없을 때, 최대 30초. 30초 뒤 미수신은 B |

## 4. QAS 3 순간 주문 폭주 (정의 변경)

| 항목 | 내용 |
|---|---|
| 부하 | 10초 동안 3,000건/초: SYM01 2,000건/초, 나머지 9종목 합계 1,000건/초. 측정 대상 매수 1주 |
| 예열 | 폭주 전 100건/초 15초. 예열 주문은 집계하지 않는다 |
| 시작·종료 | QAS 2와 같다 |
| 판정 | **주문 제출부터 2초 안에 체결 알림을 받지 못한 비율 < 0.1%**. 분모는 계획한 30,000건, 즉 실패 29건 이하 |
| 실패 | 2초 안에 체결 알림이 없는 주문: B~E, 2초 넘어 받은 A, 원인이 앱 응답 지연인 F |
| 미전송과 판정 | 앱 응답 지연이 원인인 미전송은 실패로 센다. 생성기 원인이면 회차 무효. 판단 불가면 판정 보류(1.7) |
| 관찰 종료 | 마지막 주문 + 2초 후 판정, 이후 30초 더 관찰해 늦게 온 알림과 B를 구분 기록 |

정의 변경(가이드 §10 반영): 이전 결과는 "체결 또는 대기 등록 완료"였다. 즉시 체결 가능한 1주 주문의 **체결 알림**으로 바꿨다.
QAS 2와 결과 기준을 통일하기 위해서다. 체결은 대기 등록보다 무거운 경로(양쪽 정산, 계좌 잠금 2개, 알림 2건)라 같은 2초 기준이 더 엄격한 조건에 적용되며,
**이전 정의의 결과와 같은 조건의 개선·악화로 직접 비교할 수 없다.**

## 5. QAS 5 체결 알림 (단절 후 재연결)

### 5.1 조건

| 항목 | 내용 |
|---|---|
| 부하 | 측정 대상 매수 1,000건/초. 체결마다 매수자·매도자에게 체결 알림 1건씩, 약 2,000건/초(예상) |
| SSE | 매수 500 + 매도 500 = 1,000개 |
| 단절 | **1,000개를 동시에** 끊고 5초 뒤 각자 `Last-Event-ID`로 재연결. **동시 재연결 부하가 포함된 조건**이다 |
| 한 회차 | 단절 5초 + 안정(모든 연결이 다시 붙고 `:replayed` 표시를 받을 때까지, 최대 30초) |
| 회차 수 | 한 회차 단절 구간 체결 알림 약 10,000건(예상). **누적 분모 10만 건 이상**이 될 때까지 반복, 예상 10~11회 |
| 중단 조건 | 매 회차 전 호가창 API로 남은 사전 매도를 확인해, 다음 회차 예상 소비 × 1.5보다 적으면 그 회차를 시작하지 않는다. 이때 분모가 10만 미만이면 "규모 미달"로 기록하고 합격으로 표시하지 않는다 |

### 5.2 단절 구간 정의: 서버 표시 사용 (시계에 의존하지 않음)

- 수집기는 끊기 직전 연결마다 마지막으로 받은 알림 번호 `L(a, e)`(계좌 a, 회차 e)를 기록한다.
- 재연결하면 서버는 `L` 이후 밀린 알림을 보낸 뒤 **`:replayed R`** 주석을 보낸다. `R`은 그때 읽은 마지막 알림 번호다(앱 변경).
- ADR 0003으로 같은 계좌의 알림 번호 순서는 커밋 순서와 같다. 따라서 `(L, R]`은 **그 계좌에 단절 시작부터 재구독까지 커밋된 알림 전부**이고, 생성기·RDS 시계, INSERT와 커밋의 시차, T2 시간에 의존하지 않는다.
- 한계: 이 구간은 순수한 5초가 아니라 "단절 5초 + 재연결 요청이 서버에서 처리될 때까지"다. 회차마다 구간 알림 수와 생성기가 잰 단절 시간을 함께 기록한다.

### 5.3 집계 (구분해서 표시)

| 구분 | 분모 | 누락 | 중복 |
|---|---|---|---|
| **단절 구간(판정)** | DB 체결 알림 중 단절 계좌의 `(L, R]` | 관찰 종료까지 그 계좌 수집기가 받지 못한 것 | 같은 알림 번호를 2번 이상 받은 것 |
| 재연결 전후 전체 | 단절 계좌의 `L` 이후 관찰 종료까지 모든 알림 | 같음 | 같음 |
| 알림 생성 | `trades` 기준 (체결, 매수 계좌)·(체결, 매도 계좌) 짝 | `notifications`에 없는 짝(생성 누락) | 같은 짝이 2행 이상 |
| 참고: `created_at` 구간 | 단절 시각 사이 `created_at` | — | — |

- 회차 사이 구간이 겹치지 않으므로 알림 하나는 많아야 한 회차에 속한다. 알림 번호로 한 번만 센다.
- **판정**: 단절 구간 누락 수 ÷ 분모 ≤ 0.001%. 실제 분모, 누락, 중복, 회차별 건수를 기록한다.
- 생성 누락(알림이 저장되지 않음)과 전달 누락(저장됐지만 받지 못함)을 따로 기록한다.
- 단절 중 실제로 체결 알림이 생겼는지: 회차별 분모 > 0과 계좌별 분포를 기록한다.
- `created_at` 구간은 시계와 커밋 시차에 의존하므로 판정에 쓰지 않는다.
- **관찰 종료**: 마지막 회차 뒤 부하를 멈추고, 각 계좌가 DB의 그 계좌 마지막 알림 번호까지 받을 때까지, 최대 60초.

### 6.2 수집기 자체 점검

- 받는 순간 시각을 먼저 찍고, 파일 기록은 별도 스레드가 한다. 1초마다 받은 건수, 기록 대기열 길이, 가장 오래 대기한 시간을 남긴다.
- 수집기 프로세스의 CPU·GC 시간을 기록한다.
- 기록 누락: k6가 센 전송 수 = k6 기록 행 수, 수집기가 센 수신 수 = 수집기 기록 행 수.
- 받은 알림 수를 DB의 같은 계좌 알림 수와 비교한다.

### 6.3 대조 데이터 경로

- **측정하는 동안만 RDS 보안 그룹에 생성기 보안 그룹의 3306을 허용**한다. 생성기는 앱 EC2와 같은 IAM 역할이라 DB 비밀번호(Parameter Store)를 읽을 수 있고, `mysql` 클라이언트는 Docker로 쓴다.
  ADR 0011(RDS는 앱 EC2에서만)과 다르므로 규칙을 만든 시각과 지운 시각을 측정 기록에 남긴다.
- 기록 파일은 별도 스키마 `measure`에 넣는다. `LOAD DATA LOCAL INFILE`이 RDS 기본 설정에서 막혀 있으면 묶음 INSERT로 넣는다(로컬 검증 때 확인).
- **적재·대조와 시계 차이 측정(`SELECT NOW(6)`)은 각 시험의 부하와 관찰이 끝난 뒤에만** 하고, 끝나야 다음 시험의 초기화를 시작한다. 각 작업의 시작·끝 시각을 기록한다.

### 6.4 로컬 검증

`deploy/compose.yml` + `compose.local-db.yml`로 앱을 띄우고 작은 규모(예: 50건/초, 20초)로 돌린다.

- 분류 A~G: C는 사전 매도를 일부러 모자라게, D·E는 앱을 강제 종료해서, G는 판정 SQL에 가짜 데이터를 넣어 확인한다. C의 원인 판정(1.6)도 확인한다.
- QAS 5 단절 2~3회: `(L, R]` 분모, 누락(수집기가 일부러 틀린 Last-Event-ID를 보내 만든다), 중복, 생성 누락 계산.
- 시계: k6와 수집기 기록이 같은 벽시계 기준인지.
- `LOAD DATA LOCAL INFILE` 사용 가능 여부.

## 8. 데이터 준비·정리와 순서

시험마다 **측정용 seed로 초기화 → 앱 재시작**(종목 엔진을 seed 상태로 다시 만든다)에서 시작한다. 앞 시험의 주문·알림·종목 수가 다음 시험에 남지 않는다.

| 순서 | 시험 | 시작 상태 | 비고 |
|---|---|---|---|
| 1 | 보정 | 고정 응답 서버 | 앱·DB 상태와 무관 |
| 2 | QAS 2 | seed + 사전 매도(종목당 9,000) | |
| 3 | QAS 3 | seed + 사전 매도(SYM01 25,000, 나머지 1,500) | |
| 4 | QAS 5 | seed + 사전 매도(종목당 33,000) | |
| 5 | QAS 4 재측정 | 데모 seed(1회차와 같은 계좌 1,000·보유) + 대기 주문 10만 | 아래 표 |
| 6 | QAS 6 | 측정용 seed(10종목) | 끝나면 종목 20개라 **마지막에 둔다** |

QAS 6 뒤에 다른 시험을 하려면 seed로 초기화하고 앱을 재시작한다. seed가 종목을 10개로 되돌려도 실행 중인 엔진은 20개 그대로이기 때문이다.
